# 本地空间隔离与数据库迁移设计

## 1. 背景与目标

当前应用是单用户桌面应用，业务数据保存在本地 SQLite 数据库中。第一阶段不提供登录、云端接口、后台同步或本地空间管理页面，但需要在数据库层预留可靠的用户隔离和未来同步能力。

本设计的目标是：

- 让当前数据明确归属于一个本地空间。
- 让所有业务查询和写入在 Rust 后端自动绑定当前空间。
- 在未来支持云端账号、本地数据合并和同步时，不需要重新设计核心业务表。
- 将删除改为可同步的软删除。
- 安全迁移现有旧数据库，并在迁移失败时保护用户数据。

## 2. 范围

### 本阶段包含

- `local_spaces` 本地空间表。
- `settings.current_space_id` 当前空间配置。
- `events`、`projects`、`actions` 的空间字段和同步基础字段。
- SQLite `PRAGMA user_version` 版本迁移。
- 启动备份、迁移前备份、迁移失败恢复和失败副本。
- 事件、项目、行动的软删除及既定级联规则。
- 旧数据迁移到默认本地空间。
- 示例数据不作为当前阶段必需功能；若未来启用，仅允许全新数据库生成。

### 本阶段不包含

- 登录页面、邮箱密码登录、微信登录。
- 云端 API、同步任务、冲突解决 UI。
- 本地空间切换、新建、删除界面。
- 手动 JSON 导入导出。
- 软删除记录恢复入口。

## 3. 方案比较

### 方案 A：单数据库加 `space_id`（采用）

在现有 SQLite 数据库中增加 `local_spaces`，业务表增加非空 `space_id`，由 Rust 后端注入当前空间。

优点是改动集中、保留现有关系和事务逻辑、备份仍然只需要处理一个数据库文件，也最适合未来在同一数据模型上接入同步。代价是所有查询必须统一增加空间和软删除条件，迁移需要重建受影响的 SQLite 表。

### 方案 B：每个空间独立数据库文件

通过不同数据库文件实现物理隔离。隔离边界直观，但需要管理多个连接、多个备份目录和数据库切换；未来合并与同步也要额外实现跨文件数据关联，超出当前阶段需要。

### 方案 C：每个空间独立 JSON 文件

实现初期简单，但不适合当前已有的外键关系、状态级联、事务和未来数据规模，放弃此方案。

## 4. 数据模型

### 4.1 `local_spaces`

```sql
CREATE TABLE local_spaces (
    space_id TEXT PRIMARY KEY,
    cloud_user_id TEXT,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);
```

- `space_id` 使用 UUID v4 字符串，同时作为未来云端空间标识。
- `cloud_user_id` 当前为空，未来绑定邮箱或微信账号。
- 当前只有一个默认空间，不在 UI 中展示 UUID。
- 复制数据库到另一台电脑时保留原 `space_id`，视为同一数据空间。

### 4.2 `settings`

继续使用键值表，并写入：

```text
key = current_space_id
value = 当前空间 UUID
```

如未来启用示例数据，初始化标记归属于数据库初始化流程；只有新数据库创建的默认空间允许生成示例链路。

### 4.3 业务表公共字段

`events`、`projects`、`actions` 均增加：

```sql
space_id TEXT NOT NULL REFERENCES local_spaces(space_id),
sync_id TEXT NOT NULL UNIQUE,
deleted_at INTEGER
```

现有整数 `id` 保留，用于本地关联和 UI API 兼容。迁移旧记录时为每条记录生成新的 UUID v4 `sync_id`。`updated_at`、`deleted_at` 使用 Unix 毫秒时间戳；现有秒级时间戳数据在迁移时统一转换为毫秒。

### 4.4 关系约束

- 一个事件最多关联一个项目。
- 项目只能由事件转换创建。
- 项目创建时，事件下已有直接行动迁移到项目下。
- 事件转换为项目后，不允许新建直接关联该事件的行动。
- 行动最多关联事件或项目之一，也可以无关联。
- 所有关联 ID 必须在当前 `space_id` 内校验，不能跨空间引用。

## 5. 访问边界

前端 API 类型不增加 `space_id` 输入字段。Rust 后端提供当前空间解析逻辑：

1. 从 `settings.current_space_id` 读取当前空间。
2. 校验该空间存在。
3. 所有读操作增加当前空间条件和 `deleted_at IS NULL` 条件。
4. 所有写操作自动写入当前空间，并校验被操作记录属于当前空间且未软删除。
5. 事务内的关联更新继续使用同一空间条件，防止整数 ID 在未来多空间场景下误关联。

默认列表、统计、行动计数和项目/事件完成判断均排除软删除记录。已软删除的来源项目仍保留在数据库中，因此事件不能因为“列表中看不到项目”而再次转换创建项目。

## 6. 软删除规则

删除时不执行物理 `DELETE`，而是在事务中写入 `deleted_at` 和新的 `updated_at`。

- 删除未转项目事件：软删除事件和其全部未删除直接行动。
- 删除已转项目事件：软删除事件、来源项目和项目下全部行动。
- 删除项目：软删除项目、来源事件和项目下全部行动。
- 删除单条行动：只软删除行动；项目至少保留一条未删除行动。
- 已完成或已放弃行动的历史状态保持不变，除非其所属对象的级联软删除要求记录隐藏。
- 当前不提供恢复软删除记录的入口。

软删除记录永久保留，未来只有在云端确认同步完成后才允许清理。

## 7. 迁移策略

### 7.1 版本控制

使用 SQLite `PRAGMA user_version`。应用启动时自动检查版本并执行增量迁移；迁移成功后才更新版本号。

### 7.2 新数据库

新数据库创建最新结构、默认本地空间和 `current_space_id`；当前阶段不要求生成示例事件、项目和行动。后续创建的本地空间（未来功能）默认不生成示例数据。

### 7.3 旧数据库

旧数据库迁移到新建的默认本地空间：

- 保留事件、项目、行动原有整数 ID。
- 保留所有合法数据和关系。
- 为事件、项目、行动生成 `sync_id`。
- 将旧时间戳转换为 Unix 毫秒。
- 不生成示例数据。
- 对新增必填字段和外键采用 SQLite 内部重建表。

发现无法识别的结构、缺失必要关系或异常数据时，迁移直接失败，不自动修复、不跳过记录。

### 7.4 备份与失败恢复

数据库目录下使用 `backups` 子目录。每次应用启动备份一次，并在实际迁移前额外备份一次；启动备份默认覆盖上一份同类备份，仅保留最近一份。

- 启动备份失败：记录错误并提示用户，允许继续进入应用，提示中提供立即重试。
- 备份无法读取或损坏：保留原文件并记录错误，不自动删除。
- 迁移失败：保留失败数据库副本，使用迁移前备份恢复。
- 恢复成功：允许进入应用，并提示已恢复到迁移前版本。
- 恢复失败：阻止进入主界面，保留当前数据库、备份和失败副本，并显示明确错误信息。

备份成功不弹出提示。备份实现必须使用安全的文件复制/替换流程，避免在备份过程中覆盖掉唯一可恢复副本。

## 8. 未来云同步预留

本阶段不实现登录或同步，但字段和行为遵循以下约定：

- 未来支持邮箱密码登录和微信登录。
- 首次登录提供“合并本地数据”或“从空白云端空间开始”。
- 合并时本地与云端数据合并。
- 冲突初期按最后更新时间处理，云端服务器时间作为最终标准。
- 退出云端后保留本地数据并停止同步。
- 一个本地空间绑定一个云端账号；退出后保留绑定关系。

## 9. 错误处理

数据库初始化和迁移错误必须从 Rust 层返回结构化、可读的错误信息。迁移无法恢复时不得启动带有不确定数据状态的主界面。业务命令错误不得通过前端自行推断或补写关联状态。

## 10. 验收标准

- 全新数据库只创建一个默认空间；示例数据不作为当前阶段验收项。
- 启动后所有事件、项目、行动只显示当前空间的未删除记录。
- 前端无法通过命令参数读取或修改其他空间数据。
- 旧数据库迁移后原有 ID、关系、状态和内容保持一致，并生成空间与同步字段。
- 删除事件、项目、行动不会物理删除记录，默认查询隐藏它们。
- 删除级联规则和“已转项目不可重复转换”规则保持成立。
- 迁移前备份存在；迁移失败可恢复时应用回退到迁移前版本。
- 启动备份失败不阻止应用使用，且可以重试。
- `npm run build` 通过。
- `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` 通过。
- `cargo check --manifest-path src-tauri/Cargo.toml` 在具备 Windows MSVC 链接器的环境中通过。
