# 自动更新发布指南

本文说明 LifePlan Windows 与 macOS 自动更新的密钥、GitHub Actions 配置、版本发布和发布后核查流程。

> **安全原则：** Tauri 更新签名私钥只能保存于受控的本机安全存储或 GitHub Actions Secrets。不要将私钥、密码、证书文件或其 Base64 内容写入源码、文档、Issue、Release 说明或终端截图。

## 一次性配置

### 1. 生成 Tauri 更新签名密钥

在受保护的本机环境执行以下命令。命令会交互式要求设置密钥密码；请使用密码管理器妥善保存。

```powershell
npm run tauri signer generate -w "$HOME\.tauri\lifeplan-updater.key"
```

生成后会得到以下文件：

- `$HOME\.tauri\lifeplan-updater.key`：**私钥**，严禁提交或外发。
- `$HOME\.tauri\lifeplan-updater.key.pub`：公钥，可写入客户端配置。

读取公钥：

```powershell
Get-Content "$HOME\.tauri\lifeplan-updater.key.pub"
```

将输出的**完整公钥文本**填入 `src-tauri/tauri.conf.json` 的：

```json
{
  "plugins": {
    "updater": {
      "pubkey": "此处替换为完整公钥文本"
    }
  }
}
```

公钥不是文件路径，也不要把私钥内容填入此处。已发布客户端内置此公钥，用于验证下载的更新包签名。

### 2. 准备 GitHub Actions Secrets

仅在需要将私钥复制到 GitHub 仓库 Secret 输入框时，在本机读取私钥：

```powershell
Get-Content "$HOME\.tauri\lifeplan-updater.key" -Raw
```

进入 GitHub 仓库 `9527GC/LifePlan`：

```text
Settings → Secrets and variables → Actions → New repository secret
```

创建以下两个 Repository secrets：

| Secret 名称 | 填写内容 | 注意事项 |
| --- | --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | 上述私钥文件的完整内容 | 仅粘贴到 GitHub Secret；不得写入任何仓库文件。 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 生成私钥时设置的密码 | 若生成时未设置密码，仍创建该 Secret，并保留为空值。 |

不要在工作流日志、调试输出或 `echo` 命令中输出这些 Secret。若怀疑私钥泄露，应立即停止发布，生成新密钥，并评估已发布客户端的迁移方案；旧客户端只信任内置的旧公钥，不能直接验证使用新密钥签名的更新包。

## 发布版本

### 1. 更新版本号

每次正式发布前，将下列三个文件中的版本号同步为同一个合法语义化版本，例如 `1.0.4`：

- `package.json`
- `src-tauri/Cargo.toml`
- `src-tauri/tauri.conf.json`

版本号必须高于已发布版本；不要重新使用已经发布过的版本号或标签。

### 2. 本地构建检查

发布前先执行：

```powershell
npm run build
cargo check --manifest-path src-tauri/Cargo.toml
git diff --check
git status --short
```

确认前端构建、Rust 检查均成功，且没有意外改动后再继续。实际 Windows/macOS 更新包会由 GitHub Actions 在对应 runner 上构建和签名。

### 3. 提交、推送并创建标签

以下命令以发布 `1.0.4` 为例。请按实际版本号替换：

```powershell
# 同步 package.json、src-tauri/Cargo.toml、src-tauri/tauri.conf.json 的版本后：
npm run build
git add package.json src-tauri/Cargo.toml src-tauri/tauri.conf.json
git commit -m "发布：LifePlan 1.0.4"
git push github main
git tag v1.0.4
git push github v1.0.4
```

推送 `v1.0.4` 标签会触发 `发布 LifePlan` 工作流。工作流使用上述 GitHub Secrets 对 updater 产物签名，并创建或更新同名 GitHub Release。

如当前远程名称不是 `github` 或默认分支不是 `main`，先使用以下命令确认并按实际名称调整推送命令：

```powershell
git remote -v
git branch --show-current
```

## GitHub Release 核查

工作流完成后，在 GitHub Release 页面打开对应标签（例如 `v1.0.4`），核查以下内容。

### 1. 工作流状态

确认 Windows x64、macOS Apple Silicon（arm64）和 macOS Intel（x64）构建任务均成功。任一任务失败时，不应把该 Release 视为可用更新版本。

### 2. 更新清单

下载或打开 Release 附件中的 `latest.json`，确认：

- `version` 与发布版本一致；
- `platforms` 同时包含 `windows-x86_64`、`darwin-aarch64` 和 `darwin-x86_64`；
- 每个平台都有对应的 `url` 与 `signature`；
- 每个 `url` 都指向当前 Release 中可公开访问的更新包。

### 3. 更新包和签名文件

确认 Release 中存在每个平台的更新包及其对应 `.sig` 签名文件：

- Windows x64：NSIS 更新安装包及 `.sig`；
- macOS Apple Silicon：arm64 `.app.tar.gz` 及 `.sig`；
- macOS Intel：x64 `.app.tar.gz` 及 `.sig`。

不要手工改写 `.sig`、`latest.json` 中的签名或更新包文件名；变更任一项都会导致客户端签名验证失败。可在未登录 GitHub 的浏览器窗口中逐个打开 `latest.json` 及其更新 URL，确认用户可公开下载。

### 4. 真实更新验证

使用低于该 Release 的已安装正式版客户端，在 Windows、Apple Silicon Mac 和 Intel Mac（条件允许时）分别验证：

1. 启动旧版本并进入主界面；
2. 等待后台检查完成；
3. 确认 Logo 后显示圆形下载图标；
4. 点击图标，确认出现下载中状态且不能重复触发；
5. 下载完成后确认安装器执行、客户端重启；
6. 重启后确认版本已更新；
7. 断网或故意使用无效更新源时，确认客户端仍可正常使用且不显示更新入口。

## macOS 正式分发说明

本项目的 Tauri updater 签名用于校验更新包完整性，**不能替代 Apple 的代码签名和公证**。

当前自动更新链路未配置 Apple Developer 证书、Developer ID Application 签名或 Apple notarization（公证）。因此，macOS 用户首次从网页下载或安装应用时，Gatekeeper 可能显示“无法验证开发者”“应用已损坏”或阻止启动。用户即使完成一次手动放行，后续更新也可能继续受系统签名策略影响。

在向外部用户正式分发 macOS 版本前，应完成：

1. 加入 Apple Developer Program；
2. 创建并安全保存 `Developer ID Application` 证书；
3. 在 macOS GitHub Actions 构建中导入证书并对 `.app` 签名；
4. 使用 Apple 提供的凭据提交 notarization，并在通过后 stapling 公证票据；
5. 在干净的未登录测试 Mac 上验证 DMG/应用首次启动和 updater 更新。

Apple 证书、App 专用密码、团队 ID、私钥及其导出文件同样必须存入 GitHub Actions Secrets 或其他受控密钥系统，不能提交到仓库。

## 常见问题

### 更新图标没有出现

检查当前安装版本是否低于 `latest.json` 的版本；确认 `latest.json` 可公开访问、平台键匹配当前系统，并确认客户端内置的 updater 公钥与发布签名私钥属于同一密钥对。网络异常或未发现更新时，客户端按设计不会显示图标。

### 下载后签名验证失败

确认更新包没有在签名后被重新压缩、重命名为不同内容或替换；确认 `latest.json` 中的 `signature` 与该更新包的 `.sig` 内容一致；确认工作流使用的是创建公钥时配套的私钥。

### macOS 无法打开应用

内部测试可按系统“隐私与安全性”提示人工放行。对外发布不应把人工放行作为常规使用流程，应补充 Developer ID Application 签名和 notarization。
