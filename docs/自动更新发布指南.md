# 自动更新发布指南

本文说明 LifePlan Windows 与 macOS 自动更新的密钥、GitHub Actions 配置、版本发布、自动更新日志与发布后核查流程。

> **安全原则：** Tauri 更新签名私钥只能保存于受控的本机安全存储或 GitHub Actions Secrets。不要将私钥、密码、证书文件或其 Base64 内容写入源码、文档、Issue、Release 说明或终端截图。

## 一次性配置

### 1. 生成 Tauri 更新签名密钥

在受保护的本机环境执行以下命令。命令会交互式要求设置密钥密码；请使用密码管理器妥善保存。

```powershell
npm run tauri signer generate -w "$HOME\.tauri\lifeplan-updater.key"
```

生成后会得到以下文件：

- `$HOME\.tauri\lifeplan-updater.key`：**私钥**，严禁提交或外发。
- `$HOME\.tauri\lifeplan-updater.key.pub`：公钥，可写入客户端配置。

读取公钥：

```powershell
Get-Content "$HOME\.tauri\lifeplan-updater.key.pub"
```

将输出的**完整公钥文本**填入 `src-tauri/tauri.conf.json` 的：

```json
{
  "plugins": {
    "updater": {
      "pubkey": "此处替换为完整公钥文本"
    }
  }
}
```

公钥不是文件路径，也不要把私钥内容填入此处。已发布客户端内置此公钥，用于验证下载的更新包签名。

### 2. 准备 GitHub Actions Secrets

仅在需要将私钥复制到 GitHub 仓库 Secret 输入框时，在本机读取私钥：

```powershell
Get-Content "$HOME\.tauri\lifeplan-updater.key" -Raw
```

进入 GitHub 仓库 `9527GC/LifePlan`：

```text
Settings → Secrets and variables → Actions → New repository secret
```

创建以下 Repository secret：

| Secret 名称 | 填写内容 | 注意事项 |
| --- | --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | 上述私钥文件的完整内容 | 仅粘贴到 GitHub Secret；不得写入任何仓库文件。 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 生成私钥时设置的密码 | 若生成时未设置密码，仍创建该 Secret，并保留为空值。 |

不要在工作流日志、调试输出或 `echo` 命令中输出这些 Secret。若怀疑私钥泄露，应立即停止发布，生成新密钥，并评估已发布客户端的迁移方案；旧客户端只信任内置的旧公钥，不能直接验证使用新密钥签名的更新包。

## 发布版本

### 1. 同步版本号

每次发布前，将下列三个文件同步为同一个合法的语义化版本，例如 `1.0.5`：

- `package.json`：前端、新手引导轮播显示的版本号来源；
- `src-tauri/Cargo.toml`：Tauri/Rust 客户端版本；
- `src-tauri/tauri.conf.json`：Tauri 打包和更新元数据版本。

版本号必须高于已发布版本；不要重新使用已发布的版本号或标签。发布标签必须是同一版本号加前缀 `v`，例如三个文件均为 `1.0.5` 时，只能推送 `v1.0.5`。

> 工作流的“校验版本并生成更新日志”任务会再次严格校验这三处与标签去掉 `v` 后完全一致。任一不一致都会在构建前失败，既不会发布安装包，也不会创建或更新 Release。

### 2. 发布前本地检查

完成版本同步后，先运行：

```powershell
npm run test:release
node --check scripts/release/release-utils.mjs
node --check scripts/release/prepare-release.mjs
node --check scripts/release/validate-release-assets.mjs
npm run build
cargo check --manifest-path src-tauri/Cargo.toml
git diff --check
git status --short
```

确认提交分类测试、Node 脚本语法、前端构建和 Rust 检查均成功，并核对 `git status --short` 没有意外文件后再继续。实际 Windows/macOS 更新包会由 GitHub Actions 在相应 runner 上构建和签名。

### 3. 提交、推送并创建标签

以下命令以发布 `1.0.5` 为例；请替换为实际版本号：

```powershell
# 已同步 package.json、src-tauri/Cargo.toml、src-tauri/tauri.conf.json 的版本后：
git add package.json src-tauri/Cargo.toml src-tauri/tauri.conf.json
git commit -m "发布：LifePlan 1.0.5"
git push github main
git tag v1.0.5
git push github v1.0.5
```

推送 `v1.0.5` 标签会触发 `发布 LifePlan` 工作流。工作流使用 GitHub Actions Secrets 签名 updater 产物，并在全部构建和资产校验通过后创建或更新同名 GitHub Release。

如当前远程名称不是 `github` 或默认分支不是 `main`，先使用以下命令确认并按实际名称调整推送命令：

```powershell
git remote -v
git branch --show-current
```

## 自动更新日志与 Release 正文

推送 `vX.Y.Z` 标签后，工作流会读取上一个 `v*` 标签到当前标签之间的 Git 提交标题，并自动分类：

| 提交标题前缀 | 展示分类 |
| --- | --- |
| `feat:` 或 `feat：` | ✨ 新增功能 |
| `fix:` 或 `fix：` | 🐛 问题修复 |
| `perf:`、`refactor:`（中英文冒号均可） | ⚡ 优化改进 |
| 其他标题 | 🔧 其他更新 |

工作流会自动完成以下事项：

1. 在仓库根目录 `CHANGELOG.md` 顶部插入 `## vX.Y.Z（YYYY-MM-DD）` 及本次分类更新；日期使用北京时间（`Asia/Shanghai`）。
2. 以 `github-actions[bot]` 身份将更新日志提交到默认分支，提交信息为 `docs: 自动更新 CHANGELOG vX.Y.Z [skip changelog]`。带有 `[skip changelog]` 的自动提交会在下次生成时被过滤，不会被误写进下一版更新内容。
3. 并行构建 Windows x64、macOS Apple Silicon 和 macOS Intel 安装包；汇总任务只会在三项构建均成功、资产完整且签名一致时发布。
4. 使用同一份分类更新生成 Release 正文：展示本次更新、按操作系统分类的下载表格，以及指向完整 `CHANGELOG.md` 的“历次版本更新记录”链接。
5. 汇总并上传三个用户安装包、跨平台 `latest.json`、各平台 updater 更新包及对应 `.sig` 签名文件。

`CHANGELOG.md` 的版本条目由工作流维护，请不要手动新增、修改或删除其中的版本条目。需要调整某次发布内容时，应在推送标签前修正对应提交标题；不要在 Release 正文或 CHANGELOG 中手工补写不同来源的说明。

## GitHub Release 核查

工作流完成后，在 GitHub Release 页面打开对应标签（例如 `v1.0.5`）并执行以下核查。

### 1. 工作流状态

1. 确认 `校验版本并生成更新日志` job 成功，且默认分支出现由 `github-actions[bot]` 创建的自动 CHANGELOG 提交。
2. 确认 Windows x64、macOS Apple Silicon（arm64）和 macOS Intel（x64）三个构建任务全部成功。
3. 确认唯一的 `发布 Release` 汇总 job 成功；任一准备、构建或资产校验任务失败时，不应把该 Release 视为可用更新版本。

### 2. Release 正文与下载链接

1. 确认“本次更新”按新增、修复、优化、其他分类展示，内容与该版本提交相符。
2. 确认下载表格同时包含 Windows x64、macOS Apple Silicon 和 macOS Intel，并逐个点击验证链接下载的是对应架构的资产。
3. 确认正文底部的 `CHANGELOG.md` 链接可打开，新版本位于历史记录最顶部，标题含北京时间日期。

### 3. 更新清单、资产与签名

下载或打开 Release 附件中的 `latest.json`，确认：

- `version` 与发布版本一致；
- `platforms` 同时包含 `windows-x86_64`、`darwin-aarch64` 和 `darwin-x86_64`；
- 每个平台都有对应的 `url` 与 `signature`；
- 每个 `url` 都指向当前 Release 中可公开访问的更新包。

同时确认 Release Assets 中至少包括：

- Windows x64 用户安装包，以及 NSIS updater 更新包和对应 `.sig`；
- macOS Apple Silicon 用户安装包、`.app.tar.gz` updater 更新包和对应 `.sig`；
- macOS Intel 用户安装包、`.app.tar.gz` updater 更新包和对应 `.sig`；
- 唯一的跨平台 `latest.json`。

不要手工改写 `.sig`、`latest.json` 中的签名或更新包文件名；变更任一项都会导致客户端签名验证失败。可在未登录 GitHub 的浏览器窗口中逐个打开 `latest.json` 及其更新 URL，确认用户可公开下载。

### 4. 真实更新验证

使用低于该 Release 的已安装正式版客户端，在 Windows、Apple Silicon Mac 和 Intel Mac（条件允许时）分别验证：

1. 启动旧版本并进入主界面；
2. 等待后台检查完成；
3. 确认 Logo 后显示圆形下载图标；
4. 点击图标，确认出现下载中状态且不能重复触发；
5. 下载完成后确认安装器执行、客户端重启；
6. 重启后确认版本已更新，新手引导轮播版本、客户端版本及 Release 标签去掉 `v` 后的版本完全一致；
7. 断网或故意使用无效更新源时，确认客户端仍可正常使用且不显示更新入口。

## 常见失败与排查

### 版本校验失败

工作流会列出标签期望版本及 `package.json`、`Cargo.toml`、`tauri.conf.json` 的实际版本。修正三个文件，使其都与标签去掉 `v` 后完全一致；提交并推送修复后，删除错误的远端标签，再从修复后的提交创建并推送一个未使用的正确标签。不要将不同版本内容覆盖到已有正式标签。

### CHANGELOG 推送失败

检查默认分支保护规则、GitHub Actions 的 `contents: write` 权限，以及是否允许 `github-actions[bot]` 推送默认分支。未修复前不要手动创建同标签 Release；解决权限或保护规则问题后，应从修复后的代码重新创建未使用标签并触发完整流程。

### 缺少平台资产或资产校验失败

查看对应 Windows、macOS Apple Silicon 或 macOS Intel 构建 job 的 Tauri 日志，确认用户安装包、updater 更新包和 `.sig` 均成功生成。修复工作流或构建问题后，重新运行同一标签的工作流；汇总 job 会创建或更新该标签已有的 Release，并用 `--clobber` 覆盖同名资产。若失败发生在发布前，优先从修复后的提交创建新标签，避免正式标签指向不完整构建。

### 更新图标没有出现

检查当前安装版本是否低于 `latest.json` 的版本；确认 `latest.json` 可公开访问、平台键匹配当前系统，并确认客户端内置的 updater 公钥与发布签名私钥属于同一密钥对。网络异常或未发现更新时，客户端按设计不会显示图标。

### 下载后签名验证失败

确认更新包没有在签名后被重新压缩、重命名为不同内容或替换；确认 `latest.json` 中的 `signature` 与该更新包的 `.sig` 内容一致；确认工作流使用的是创建公钥时配套的私钥。

### macOS 无法打开应用

内部测试可按系统“隐私与安全性”提示人工放行。对外发布不应把人工放行作为常规使用流程，应补充 Developer ID Application 签名和 notarization。

## 首次自动化发布演练

首次启用自动发布时，选择一个尚未使用的预发布版本，例如 `1.0.5-rc.1`。将 `package.json`、`src-tauri/Cargo.toml` 和 `src-tauri/tauri.conf.json` 都改为 `1.0.5-rc.1`，完成本地检查并提交后，推送 `v1.0.5-rc.1`：

```powershell
git tag v1.0.5-rc.1
git push github v1.0.5-rc.1
```

工作流完成后：

1. 检查自动生成的 CHANGELOG 条目、Release 分类内容、三个操作系统下载链接、`latest.json` 和所有 updater 签名资产。
2. 在可用的 Windows、Apple Silicon Mac 和 Intel Mac 上执行一次真实更新验证。
3. 确认演练结果正确后，按相同流程发布正式版本 `1.0.5`；正式版必须使用新的三处版本号及新的 `v1.0.5` 标签。
4. 若任一阶段失败，修复默认分支上的代码、工作流或权限后，删除失败的远端标签，再从修复后的提交创建并推送一个未使用标签；不要把不同版本内容覆盖到已有正式 tag。

演练只通过真实 GitHub Actions 执行；不要在本地伪造 GitHub Release、伪造签名文件，或为方便测试把私钥写入环境截图、脚本和文档。

## macOS 正式分发说明

本项目的 Tauri updater 签名用于校验更新包完整性，**不能替代 Apple 的代码签名和公证**。

当前自动更新链路未配置 Apple Developer 证书、Developer ID Application 签名或 Apple notarization（公证）。因此，macOS 用户首次从网页下载或安装应用时，Gatekeeper 可能显示“无法验证开发者”“应用已损坏”或阻止启动。用户即使完成一次手动放行，后续更新也可能继续受系统签名策略影响。

在向外部用户正式分发 macOS 版本前，应完成：

1. 加入 Apple Developer Program；
2. 创建并安全保存 `Developer ID Application` 证书；
3. 在 macOS GitHub Actions 构建中导入证书并对 `.app` 签名；
4. 使用 Apple 提供的凭据提交 notarization，并在通过后 stapling 公证票据；
5. 在干净的未登录测试 Mac 上验证 DMG/应用首次启动和 updater 更新。

Apple 证书、App 专用密码、团队 ID、私钥及其导出文件同样必须存入 GitHub Actions Secrets 或其他受控密钥系统，不能提交到仓库。
