# LifePlanTodolist V1.0 技术规划

## Context

用户希望基于《小强升职记》的时间管理理念，构建一款桌面端时间管理工具。项目目录 `E:\项目\LifePlanTodolist` 当前已经具备可运行的 Tauri + React + SQLite 应用骨架，并已实现事件篮、项目行动、今日事、番茄钟、奖励池、重复行动和本地备份等功能。本规划用于记录当前真实实现和后续开发方向。本规划的目标是从零搭建一个可运行的 Tauri + React + SQLite 桌面应用，并完成 V1.0 功能边界。

## Goals

1. 实现 V1.0 完整功能闭环：事件篮 → 项目内行动 → 今日事 → 番茄钟 → 复盘。
2. 建立清晰的数据模型，支持项目/行动两层结构和项目时间预算联动；重要程度与紧急程度采用二值模型。
3. 保证番茄钟计时精准、数据本地可靠、支持自动备份。
4. 为后续 OKR/甘特图、云同步、移动端扩展预留结构。

## Technical Stack

### 后端
- **Tauri v2** + **Rust**
- **rusqlite** + 自定义 Tauri Commands（而非 `tauri-plugin-sql`）
  - 理由：需要 Rust 层处理番茄钟精确计时、项目与行动时间预算校验、自动备份等复杂逻辑，自定义 commands 更灵活。
- 数据库文件本地存储，路径由 Rust 层统一管理。

### 前端
- **React 19** + **TypeScript**
- **Vite**（Tauri 默认集成）
- **Ant Design 6**（主要 UI 组件库）
- Tailwind CSS 保留基础配置，不作为主要组件体系
  - 理由：可定制性强、按需安装、适合桌面端。
- **Zustand** 状态管理
- **React Router** 路由（Tab 内页面切换）
- **dayjs** 日期处理

### 数据
- **SQLite** 本地文件
- 表结构采用自增 ID，核心实体使用 `created_at`/`updated_at` 时间戳。
- 启动时自动执行数据库迁移（migrations），支持版本升级。

## 核心规则

### 1. 二值重要程度与紧急程度
`importance` 和 `urgency` 均为 0/1，由用户直接选择重要/不重要、紧急/不紧急，不根据截止日期自动计算多级值。

### 2. 优先级计算\n- 使用 `priority = 4 - (importance * 2 + urgency)` 计算，数字越小优先级越高。\n- P1：重要且紧急；P2：重要但不紧急；P3：不重要但紧急；P4：不重要且不紧急。

### 3. 项目-行动时间预算
- 项目直接包含行动，不设置任务层级。
- 项目预计时间与行动预计时间保持关联。

### 4. 今日事可用性
- 启动日期 > 今天：不显示在今日事中
- 启动日期 ≤ 今天：正常显示
- 已完成的行动：默认隐藏，可在过滤中查看

## Implementation Phases

### Phase 1: 项目骨架 + 数据库（1-2 天）
1. 使用 `npm create tauri-app@latest` 初始化 Tauri v2 + React + TypeScript + Vite 项目。
2. 配置基础样式，并使用 Ant Design 作为主要 UI 组件库。
3. 在 Rust 中集成 `rusqlite`，创建数据库连接和迁移机制。
4. 创建 `events`、`projects` 和 `actions` 表及对应的 CRUD Commands。
5. 创建事件篮和行动页面骨架。

### Phase 2: 事件篮 + 项目行动闭环（2-3 天）
1. 实现事件篮列表页，支持新增/编辑/删除事件。
2. 示例数据不作为当前阶段必需项。
3. 事件转项目流程。
4. 项目直接管理行动。

### Phase 3: 项目卡片与行动管理（2-3 天）
1. 项目列表视图，按优先级排序。
2. 事件篮“已转项目”Tab。
3. 项目行动列表和排序。
4. 二值重要/紧急和基于两者的优先级排序。
5. 项目状态管理。

### Phase 4: 项目拆解 + 项目内行动管理（2-3 天)
1. 项目详情区域支持添加和管理行动。
2. 不实现任务/子任务和思维导图。
3. 项目-行动预计时间关联。
4. 项目内行动列表和每日安排入口。

### Phase 5: 今日事与每日时间块（2 天）
1. 从项目内行动安排到今日事。
2. 每日时间段新增、编辑、删除和行动安排。
3. 每日计划模板和执行复盘。

### Phase 6: 番茄钟（3 天）
1. 番茄钟记录由 Rust 持久化，前端负责计时展示和交互。
2. 每日 Tab 内番茄钟 UI。
3. 完成/放弃/中断记录。

### Phase 8: 自动备份 +  polish（2 天）

2. 设置页面。

## Key Technical Decisions

### 为什么用 rusqlite 而不是 tauri-plugin-sql？
- 需要 Rust 层处理数据持久化、项目与行动时间预算校验、自动备份等逻辑。
- 自定义 commands 更灵活，便于后期扩展。
- 数据一致性在 Rust 层更容易保证。

### 为什么用 Ant Design？
- 提供成熟的表单、弹窗、标签、步骤和布局组件。
- 适合当前桌面端后台式的效率工具界面。
- 与 React + TypeScript 生态集成良好。

### 为什么用 Zustand 而不是 Redux？
- 状态管理需求中等，Zustand 足够轻量。
- 减少样板代码，加快开发速度。

## Risks & Mitigations

| 风险 | 缓解 |
|------|------|
| 番茄钟后台计时不准 | 由 Rust 层处理 timer，使用系统时间；Tauri 事件通知前端刷新 UI。 |
| 项目拆解模型保持简单 | V1.0 采用项目-行动两层卡片/列表，不引入任务树或思维导图。 |
| 时间预算联动校验复杂 | 核心校验在 Rust 层，前端只展示警告；允许用户预留缓冲。 |
| 自动备份目录权限问题 | 默认备份到应用数据目录；用户可修改，修改失败时友好提示。 |

## 当前实现约定（2026 年 9 月）

- 首页为“今日事”，因为它是高频执行页面；事件篮清理通过首页提示和每周复盘向导完成。
- 不提供独立行动清单页面，行动由项目直接管理并安排到今日事。
- 不提供独立四象限决策台；优先级仅依据重要程度和紧急程度计算。
- 不提供青蛙任务推荐算法，优先级仅根据重要程度和紧急程度计算。
- 不单独实现时间日志，今日事页面的实际结果、是否达到预期和是否专注作为复盘依据。
- 统计报表需要实现，指标至少包括完成率、完成行动数、完成番茄数、专注时长、项目状态分布、事件处理情况和每日计划达成情况。
- 当前数据库实际包含 `local_spaces`、`daily_list_items`、`daily_schedule_days`、`daily_schedule_slots`、`daily_schedule_templates`、`recurring_actions` 等表，技术模型以代码和数据库迁移为准。
